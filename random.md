Prime directive

Platform boundary — engine vs use case

DIP is one engine serving many use cases (KYC/CLM, securitization, tax ops, and future ones). The boundary is strict:
- Engine capabilities — ONE shared implementation, never per use case: classification (all layers, including vector/exemplar memory from Task 16), bundle splitting, the unknown-doc registration queue (Task 15), extraction, verification operators, the review queue, label capture and promotion, the eval harness and readiness manifest, audit, provenance, job running, and the MCP surface. These live in core. Every use case flows through the same code path.
- Use-case contributions — data and configuration, not forked logic: doc_class rule YAMLs, labeled datasets, reference data, output templates, and narrowly-scoped detectors (e.g., securitization's issuer detection) plugged in through declared extension points that the engine calls — scope-gated plugins, not copies of engine code.
- Source signals are adapters, not the spine. The shared classifier must work on content alone (content keywords, LLM, vector/exemplar) — that is the default path, because most production traffic is system-to-system with no sender and no subject. Email-based identification signals (sender domain, subject keywords, filename patterns — the current L1 ladder) become an optional signal-provider adapter: when a document genuinely arrives through the email adapter, its signals feed the shared classifier as additional evidence; when it arrives via REST/folder/MCP/scheduled pull, those signals are simply absent and contribute nothing. Never synthesize email metadata to satisfy the classifier, and never let a signal's weight count when the signal was fabricated. A use case that receives documents by email (e.g., emailed seller reports) wires this adapter for its sources; use cases that don't, don't.
- Migration duty: if, while working any task, you find classification, splitting, unknown-doc handling, or exemplar logic implemented inside a use-case package (or gated by use-case conditionals in a way that forks behavior), do not extend it there. Lift it into the shared engine behind the common interface, keep the use-case-specific part as a plugin/config, and prove no accuracy change with the regression evals before merging. A human-taught classification memory must benefit ALL use cases: an exemplar learned from a securitization reviewer and one learned from a KYC reviewer live in the same registry and are matched by the same code, scoped only by doc_class.

Task 2 — Build the eval harness and labeled datasets

What evals are (and are not). Evals are a developer-side quality measurement tool. They compare pipeline output against human-labeled ground truth and produce scores. They NEVER run inside the production document path — production correctness is handled by the verification gate (rules + withhold), which runs on every document. Evals run offline, on demand, and in CI.

Build a plain custom harness. Do not use DeepEval. There is an unmerged branch using DeepEval — do not merge it or take a dependency on it. DeepEval is oriented toward fuzzy LLM-judged scoring (relevance, faithfulness), which is the wrong tool here. Extraction correctness is exact: a value either matches labeled truth (after normalization) or it doesn't. The harness is a loop + field-by-field comparison + report. It must also incorporate signals DeepEval cannot see: withhold decisions, grounding pass/fail, and verify outcomes. You may cherry-pick generic utilities from that branch if genuinely useful, but the core comparison logic is custom. LLM-judged scoring may be considered later, for narrative fields only, as a separate opt-in — not in this task.
2a. Extraction evals. The harness takes a labeled dataset (document + hand-verified correct field values) and reports, per doc_class and per field: booked-value precision, withhold rate, grounding success rate, and error cases. Comparison must normalize before comparing (whitespace, case where type-appropriate, date/number formats per field type) so formatting noise doesn't count as a miss. Priority order for datasets: KYC tax forms (W-9, W-8BEN family) first, then EDD memo, then the rest. Where labeled data doesn't exist yet, generate the harness plus an empty labeled-data folder structure and a fill-in template so a human can provide ground truth — do not fabricate ground-truth labels yourself, ever.

2b. Classification evals. Build a confusion-matrix runner: given labeled (document → true doc_class) pairs, report per-class accuracy, and specifically flag confusion between near-identical classes (edd_memo vs edd_memo_2).
2c. The three run modes. The same harness must support all three, because these are the three moments evals run in practice:


1. Graduation run (per doc_class): run_evals --doc-class w9 — run when a developer authors or changes rules for a doc type. A doc_class is not considered "ready" until it has a labeled dataset and a passing graduation run. Add a machine-readable readiness manifest (doc_class → eval status: no-data / failing / passing) so "which doc types are actually proven" is a query, not a guess.
2. Regression run (CI): full suite runs on merge for any change touching rules, prompts, parsers, extraction, or verification. A score drop on any previously-passing doc_class blocks the merge. Wire this into the existing CI gate alongside (not replacing) the byte-diff golden gate.
3. Benchmark run (on demand): run_evals --report produces a stakeholder-shareable file (markdown + JSON) with per-doc_class precision, withhold rate, and classification accuracy — the format for the Abby-parity benchmark table.

Also: add field-level semantic comparison against labeled truth as a second test gate alongside the existing byte-diff gate, so formatting changes and value changes are distinguishable.
Acceptance test: (1) graduation run works for a single doc_class and updates the readiness manifest; (2) CI regression mode fails a merge when a deliberately-broken rule drops a previously-passing score; (3) benchmark mode emits the shareable report from at least one labeled dataset; (4) no DeepEval dependency in the merged code.

Task 20 — Resilience, fallbacks, and the quality escalation ladder

Quality is decided on the bad documents, not the good ones. Make every failure mode explicit, bounded, and visible.

Parser fallback chain: parsing runs a declared ladder (LlamaParse → LiteParse → PDFplumber → future Aiden Parse) behind one interface. Between rungs sits a parse-quality check (empty output, garbage-character ratio, page-count mismatch, missing text on pages known to have a text layer) — a "successful" parse that returns junk must fail forward to the next rung, not proceed. The parser that finally served the document is stamped in provenance (Task 13). If all rungs fail, the job lands in dead-letter (below), never silently half-processed.
Gateway resilience: all LLM-gateway calls get bounded retry with exponential backoff, honoring the known 120s hard timeout — long documents stay on the async locator pattern (narrative served from raw parse, never regenerated by the LLM); multi-pass extraction remains the documented fallback for oversized payloads, and each pass is provenance-stamped.

Field escalation ladder (quality before surrender): when a field fails verification or grounding on the first pass, the engine may make ONE bounded escalation attempt before withholding — a focused re-extraction of just the failed fields (smaller targeted prompt, optionally an alternate model via the routing adapter when available). Escalation results go through the SAME verification gates; if they still fail, withhold as normal. Escalations are capped per job, stamped in provenance, and counted in metrics — a rising escalation rate on a doc_class is a quality signal, not background noise.

Retry budget and dead-letter: every job has a retry budget (crash reclaims from Task 6 count against it). A job that exhausts its budget moves to a DEAD_LETTER state — visible on the review surface, notification emitted, document and partial results preserved, requeueable by a human after the cause is fixed. A poison document must never loop forever or vanish.

Degraded modes: if KDB.AI or Postgres is unreachable, jobs queue or fail cleanly with a clear status — never proceed with partial sinks (a document extracted but never persisted, or persisted without its coordinate map, is corruption, not progress). Startup checks verify all sinks before workers accept jobs.
Acceptance test: a deliberately corrupt PDF walks the full parser ladder, fails, lands in dead-letter with a notification, and is human-requeueable; a document whose first-pass field fails grounding gets exactly one escalation, and its provenance shows both attempts; a simulated gateway timeout retries with backoff and eventually dead-letters rather than looping; with the vector store stopped, new jobs queue cleanly and none produce partial sinks.
